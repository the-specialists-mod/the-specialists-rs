# The TS 2.1 gameplay plugin

`ts_gameplay 21` makes the server play by TS 2.1's rules, the April 2004 `mp.dll` and
`client.dll`. The decomp's reports are in `docs/ts21/` and posted on issue #100. The plugin is
the crate `crates/ts21` (package `ts21-gameplay`). It plugs into the hooks described in
[gameplay-plugins.md](gameplay-plugins.md), and the 3.0 crates never name it.

## Status

The plugin is registered on both sides and selectable end to end: the cvar, physinfo `gp`,
`SrvSett` 4 and the reset on a switch all work (issue #100 checklist item 1).

Done:

* **Item 2, shared movement:** every row of issue §2.1, speed by free slots (§2.2) and the 310
  cap ([Movement](#movement)).
* **Item 3, shared weapons:** the 2.1 tables, fire timing, spread, pellets and prediction
  ([Shared weapons](#shared-weapons-issue-100-23-checklist-item-3)).
* **Items 8, 9:** power-ups, slow motion and the server stunts
  ([Power-ups and slow motion](#power-ups-and-slow-motion-issue-100-37), [Stunts](#stunts-issue-100-38-slot-limits-35)).
* **Items 10, 14:** the map entities and the protocol translation
  ([Map entities](#map-entities-issue-100-39-checklist-item-10), [Protocol](#protocol-issue-100-12-checklist-item-14)).
* **Item 13:** the client HUD and input ([Client: HUD and input](#client-hud-and-input-checklist-item-13)).
* **Items 6, 7, 11:** the server rules, scoring, cash, cvars and commands
  ([Rules, scoring, cash, cvars and commands](#rules-scoring-cash-cvars-and-commands-issue-100-items-6-7-11)).

## Layout

| Package (directory) | Implements | Linked by |
|---|---|---|
| `ts21-gameplay` (`crates/ts21`, `src/shared/`) | `shared::gameplay::PmRules` and `GunRules` on `Ts21`: movement and the gun, which the server and the client's prediction both run (issue §2). The id `"21"` | both libraries |
| `ts21-server` (`crates/ts21/server`) | `ts_server::gameplay::ServerRules` on `Ts21Server` (issue §3), and the server's `PLUGIN` | `server-dll` |
| `ts21-client` (`crates/ts21/client`) | `ts_client::gameplay::ClientRules` on `Ts21Client`: HUD and input (issue §4), and the client's `PLUGIN` | `client-dll` |

The side hooks are packages of their own, not cargo features, so a build of both libraries never
links the server crate into the client library or the other way round
([gameplay-plugins.md](gameplay-plugins.md) §1). `server-dll` registers `ts21_server::PLUGIN`
under the id `"21"` at `GameDLLInit`, and `client-dll` registers `ts21_client::PLUGIN` at
`Initialize`. Both do it behind their default-on `ts21` feature, so `--no-default-features`
builds 3.0 alone.

## Rules

* Match TS 2.1 exactly, including its oddities, as the port matches 3.0 (AGENTS.md). Cite the
  2.1 function and address (`mp.dll`/`client.dll` VAs, `0x1000xxxx`) in doc comments.
* The wire format stays 3.0's (issue #100 §1.2). The plugin carries 2.1 values in 3.0's messages.
* Never copy behaviour that crashes, hangs or stops the engine. Guard it and list it below.

## Movement

both run it, chosen per command by physinfo `gp`, so they agree. Addresses are 2.1 `mp.dll`'s
(decomp `ts21/server-win`, report `docs/ts21/movement.md` §2). Each value was checked against the
disassembly and the constants in `.rdata`.

The rest of the movement is the same in both builds and isn't overridden. That includes the
super-jump glide: 2.1 reads it from `iuser4` bit 0x80000 (3.0: 0x100000), and its super jump
sets 0x100000 (3.0: 0x200000). The shared movement keeps 3.0's bit layout, as the wire does
(issue #100 §1.2), and the server's stunt code converts. The time scale also keeps the port's
encoding, where 1.0 is normal (2.1 uses 0), so the 2.1 guards for 0 only matter before a
player's first spawn.

### Arithmetic

* 2.1 `mp.dll` runs the x87 at 53 bits, as 3.0's does (its CRT sets `_PC_53` at 0x1006fa8b), so
  `Arith::Msvc` reproduces its finite arithmetic. The overrides reproduce its stores and
  operation order, written generically over `shared::pm::Fpu`.
* 2.1's compiler tests `fcom` through the parity flag, so its comparisons follow IEEE for a NaN
  (Rust's operators). The overrides use IEEE compares. The SDK movement code both rulesets
  share still sends a NaN 3.0's way: issue #105.
* 2.1's `client.dll` is an unoptimised build that stores every intermediate to a `float`
  (`PM_Accelerate` cl21 0x1005aef0, `FixVelocity` cl21 0x100919b0), so 2.1's own prediction
  could differ from its server in the last bit. The port predicts with the server's arithmetic
  instead, so client and server agree exactly (see Deviations).
* TS 2.1 shipped no Linux server. With the server's `ts_pm_arith gcc`, the overrides run 2.1's
  formulas with `ts_i386.so`'s rounding (every value the C stores rounded to a `float`). There is
  no 2.1 GCC build to compare against.

## Rules, scoring, cash, cvars and commands (issue #100 items 6, 7, 11)

`ts21-server` (`crates/ts21/server/src/`): `rules.rs`, `scoring.rs`, `cash.rs`, `players.rs`,
`cvars.rs`, `commands.rs`. Addresses are 2.1 `mp.dll` VAs; decomp `docs/ts21/rules.md`.

### Game modes and teams (`rules.rs`)

* **The mode comes from the map name** (`DecideGamePlay` 0x100433b0, case-sensitive prefix):
  `tm_` objective rounds (3), `tr_`/`cs_`/`de_` round team deathmatch (2), `ts_` teamplay in The
  One mode, else `mp_teamplay`. There is no worldspawn `gamemode` key. `mp_theonemode` is read at
  map load; on a map that isn't `ts_` The One still runs, on DM rules.
* **LMS is the live `lastmanstanding` cvar** in DM (Think reads it every frame), not a mode.
* **Round modes 2/3** (`InstallGameRules`, `CTSGameRules::Init` 0x10044810): teams "Specialists"
  (model `seal`) and "Mercenary" (`merc`), each with team cash `(int)initial_cash`; the first
  round starts 5 s in. `InitObjectives` makes it mode 3 when the map has a
  `ts_objective_manager` (at every round restart; at install no entity exists yet, so the first
  5 s are mode 2, as in 2.1). Specialists spawn at `info_player_start`, Mercenaries at
  `info_player_deathmatch`, and in mode 2 the sides swap every third round.
* **Rounds:** Think's round branch, `TeamWin(team, win, lose)` (0x10044d00: team cash
  `min(max(c + win, initial), 30000)` for the winner, `max(c + lose, initial)` otherwise; with
  under two players the team cash and scores start again and "Waiting other players."),
  `RestartRound` (0x100445d0: no refund, players pick up their team cash, join deadline 25 s,
  respawn in 3 s), `ResetRestartRound` (0x10044ba0, restart in 3 s; `n >= 2` also clears the team
  cash and scores), `CheckDeads` (0x10045940: LMS counts a pending respawn as standing; mode 2
  team wins and draws). `TSHVoice` and the "Specialists"/"Mercenary" `TeamScore`s.
* **Teamplay on DM maps** is the SDK's model teams: the team list is `mp_teamlist` (no 4-team
  table, no `mapteams`/`teammodels`/`mp_teammodels`), `SetDefaultPlayerTeam` reads the `model`
  key, and each team's model is its name. In The One mode the players' models and teams are
  `mp_theone` and `mp_theothers`.
* **The One:** `SetPlayerTheOne` (0x100467c0) without the speed change or log line;
  `SelectRandomTheOne` (0x100466e0) doesn't look for a One first, and Think calls it every frame
  while there is none, plus the 10 s check; after a kill The One gains 10 health per player up to
  200 (teamplay `PlayerKilled` 0x100392e0, counting slots 0..maxClients-1 as compiled); overheal
  decays to 100 for everyone, The One included, and nothing regenerates.

### Scoring (`scoring.rs`)

`TSGetPointsForFrag` (0x1004f3c0) and `PlayerKilled` (0x1004f7e0): a stunt kill +2 with no speed
test, a slide +1, both stacking on close combat (kung fu + stunt = 4); round modes score plain
points; English frag messages (`"%i frags for %s, %s"`, " style!", "Kung-Fu"); double kill
within 1 s, the last-kill time always updated; sprees +30 / +50 / health set to 150 with kung fu,
super jump and a 3 s slow pause; killing The Specialist +5 and a 3 s slow pause; no specialist
suicide penalty; no headshot/knife/katana/coldcock lines; death-cam slow point 0.15 for 1.5 s;
`slowmatch` caps the held slow motion at 5 s. A suicide or a death by a non-player takes the frag
from the **attacker's** pev (0x1004f87f): a world kill costs the world a frag and the victim
keeps its frags. Kill logs carry no 3.0 tags.

### Cash and buying (`cash.rs`, `players.rs`)

* `CashBased()` (0x100435f0): the round modes, or Think's `(int)usecash` copy non-zero.
* Join: `InitHUD` sets the cash to `(int)initial_cash` (no `ClientPutInServer` cash). The floor
  `FUN_10042c90` (team cash in the round modes, then `initial_cash`) runs at `StartObserver`,
  `Killed` and `TSInit`.
* Kill cash: points × 900, only in DM/TDM while cash-based.
* `BuyArmament`, `BuyWeapon`, `AddItem`, `BuyAmmo` (0x100559d0, 0x10055e00, 0x10055c30,
  0x10055a40): the weapon's cost and the attachments (silencer 900, laser 800, flashlight 500,
  scope 1800) are charged when cash-based and refused below 0; M61s only in the round modes, two a
  life; kevlar (1900) and stealth shoes (700) only in the round modes; kevlar sets the armour to
  100 and weighs nothing.
* `PickUpWeapon` (0x10055830) charges `free_slots − slots` with no akimbo refusal and no stack
  multiplier (`ServerRules::pick_up_cost`): a hand-typed `tkw` with the akimbo id of a single gun
  (10, 16, 30) buys the pair, built by `GiveWeapon` from the single's record, without the single.
* `Killed` in DM/TDM drops an armour power-up holding the remaining armour.
* A corpse's M61s: `DropWeapon` (FUN_10056080) has no dead-player branch, so `Killed` throws one
  M61 world gun with the drop sound, in every mode; 3.0 turns them into grenade power-ups
  (`ServerRules::dead_grenades_become_powerups`).
* Respawns (`SetPlayerRespawnTime` 0x10042d50): mode 3 by `ts_mapglobals` `playerrespawn`, mode 2
  and LMS by `respawnnumber`, join deadline 25 s.

### Cvars and commands (`cvars.rs`, `commands.rs`)

* Registered besides 3.0's: `mp_flashlight` "0", `initial_cash` "3000", `cashforwin` "1500",
  `cashforlose` "-1000", `respawnnumber` "1" (`ServerRules::cvars`; the server has the union).
  `respawntime` keeps 3.0's default "3": both clamp it to 5..30, so it plays as 2.1's "5".
* `globalslow`, `weaponrestriction` and `restartround` are cvars 2.1 polls in Think. The engine
  can't register a cvar named like a command, so 3.0's commands stay and, in 2.1 mode, act as the
  cvar: no argument prints `"name" is "value"`, an argument sets it. `globalslow` is a fraction
  clamped to 0..1 (0..2 with cheats), 1 meaning off; `weaponrestriction` 1..5 map to masks
  0, 0x01, 0x03, 0x13 and 0x1f (5 ignoring the map), sent as `SrvSett` 3 on change;
  `restartround n` restarts and goes back to 0.
* `SrvSett` 0 carries `realbullet != 0`.
* Client commands: `give <class>` (cheats), `powerup 4` stores a timed infinite clip (type 2),
  `cashala` +10000; `respawn`, `motd`, `fullupdate` and `lasclr_*` are unknown commands (an
  observer respawns with fire instead: [Observers](#observers-and-respawning-issue-113)).

### Observers and respawning (issue #113)

`observer.rs`, the `ServerRules::observer_think` hook: the `pev->iuser1 != 0` block of 2.1's
`PreThink` (0x100537e0, 0x10053b25..0x10053d63), checked in the disassembly.

* **Fire respawns.** 2.1 has no `respawn` command. While the observer holds `IN_ATTACK`: with no
  respawn this round (`m_flRespawnTime < 0`) "You have to wait until the next round." (red, once a
  second, sharing the countdown's timer `pl+0x6cc`); once `0 < m_flRespawnTime < time`, the time
  is zeroed, `StopObserver` (FUN_1005a700, 3.0's) respawns the player, and PreThink zeroes
  `impulse` and returns before the countdown and the observer buttons. The respawn timers and
  round modes are the ones `SetPlayerRespawnTime` set (`players::set_respawn_time`): in LMS and
  modes 2 and 3 a player whose respawns are used up (or whose join deadline ran out) has -1 and
  waits for the next round; otherwise the `respawntime` runs. 2.1's bots press fire for 0.1 s while dead (`bots`, `Think` bit 0x100), so they
  come back the same way.
* **Countdown.** As 3.0's, but `respawn_at - time` is truncated on the FPU, unrounded (`__ftol`).
* **Join deadline** (25 s in 2.1): its "N seconds left for respawn, press Fire to Play!" is sent
  with effect 0x11 (top of the screen, replacing; 3.0: 0x10, centred). A NaN deadline shows the
  line instead of expiring.
* **Death.** `PlayerDeathThink` (0x10052140) is 3.0's: any button but `IN_SCORE`, or the death timer
  (`pl+0x6e0`) running out, makes the corpse and starts observing. Nothing to override.
* The observer camera after it (`Observer_HandleButtons`, `Observer_Idle`) is still TS 3.0's
  (issue #115).

### Open here (other items or not yet hooked up)

* Mode 3's objective managers (`SetObjective`, `targetontimeleft`, `targetonspecdead`,
  `targetonmercdead`), `EnableObjective` and `cutwire_<n>` need 2.1's objective entities
  (item 10): until then mode 3 round expiry is a draw and its `CheckDeads` only handles the
  draw. `ts_mapglobals` `playerrespawn` isn't read yet (0, unlimited).
* `customweapons` (2.1's three-value weapons file) belongs with the 2.1 weapon tables.
* The breakable/door sweep semantics of `RespawnEntities` (item 10) come from that item: Think
  calls `respawn_entities`. (Think calls 2.1's own power-up spawner, `powerup::auto_powerups`.)

## Stunts (issue #100 §3.8, slot limits §3.5)

`crates/ts21/server/src/stunt.rs`. Decomp `docs/ts21/movement.md` §3, checked against the 2.1
code.

* **Absolute timers** (`ServerRules::stunt_clock`, `Absolute`): every stunt timer is an end time
  `gpGlobals->time + d * slowInv`, fixed when it starts, with `slowInv = 1 / max(fuser1, 0.1f)`
  (`FixedSlowMul` 0x1005a3d0, `FixedSlowAmt` 0x1005a3b0). Nothing counts them down; they run
  while `t > time` and are over once `t < time` (`Play` 0x1005acf0, `BlockPlayer`'s lock in
  `PreThink` 0x100537e0). `NextStunt` sends `trunc((next - time) * 10)`. The coyote window is
  `0.7 * slowInv`, and the weapon delays a stunt sets are `d * slowInv`. The kung-fu and katana
  timers the gun writes (`recover`, the kick cooldown, `BlockPlayer`) go through the same clock.
* **Slot limits** (`can_dive`): used slots below 22 / 42 / 72, nothing bypasses them. In the
  round modes (mode 2/3) a high stunt also needs `armorvalue <= 0` (`CanDiveHigh` 0x1005b0b0:
  `fcomp 0.0; test ah,0x41; jp` refuses above 0 or on a NaN). The decomp report and issue
  #100 §3.5 read this as "needs armour"; the code says the opposite.
* **Recoveries** (`StuntRules`): dive roll-out 0.75 (`Landing` 0x1005c4e0), flip 0.5
  (`HandleWheel` 0x1005c040), get-up 1.0 (`HandleSlide` 0x1005c1f0), wall jump/climb landing 0.5
  and it sets `RECOVER` (`HandleWallJump` 0x1005bd80, `HandleWallClimb` 0x1005bec0). Roll 0.75
  and the super-jump landing 0.75 as in 3.0; rolling out of a super-jump landing sets
  `m_flNextAttack = 0.75 * slowInv` (`PostThink` 0x10054180).
* **Keys:** roll-out and get-up take `IN_JUMP | IN_ALT1` only (`button & 0x4002`).
* **Moves:** no wall dive (`HandleStunt` 0x1005b9f0, `HandleWallClimb`); jump while gliding
  takes the wall-jump branch, not the climb; `HandleStunt` leaves the close-combat window alone;
  `GoWheel` (0x1005d0e0) and `GoRoll` (0x1005d600) don't wait for the jump kick's cooldown.
* **Recovery end** (`Play`): clears `ROLLING | GO_DUCK | RECOVER` only and leaves `BlockPlayer`'s
  lock running (3.0 also clears 0x80000 and 0x2 and ends the lock).
* **Wall chain:** `time + min(10, slowInv * max(0.5, chain))` (`GoWallJump` 0x1005b320,
  `GoWallClimb` 0x1005b550).
* **Bullet time** (`GoBulletTime` 0x1005b160): only while slowed (`fuser1 != 0` in 2.1, any time
  scale but 1 in the port), no ×0.7 dodge window, and `m_flNextAttack = 0.55 * slowInv` if it has
  run out.

### Not done here (other checklist items)

* The gun's side: 2.1's weapon timers count down in real time and its fire delays are fixed at
  fire time (`rate × slowInv`, ×6.67 under the shooter's own slow pause), and `GoSlow`'s release
  clamps `m_flNextAttack` (and the gun's two next-attack times) to 1 s (item 3). The stunt clock's
  `attack_delay` already gives `d * slowInv`, which assumes that model.
* Kung fu's ×0.1 recovery input (item 2). (The jump kick, the backflip kick and kung fu's
  `BlockPlayer(delay × 0.9)` are in "Damage", item 5.)
* `ts_powerup`'s keyvalues (item 10). (The round modes' 3 s spawn slow motion, the armour drop,
  `slowmatch`'s cap and the cheat `powerup` command are items 6, 7 and 11's, in `players.rs`,
  `lib.rs` and `commands.rs`; the armour drop sets its amount with
  `entities::ts::powerup::set_armor`.)
* Cosmetic, not ported: the animation `framerate` (2.1 sets 0 below a 0.1 time scale), the
  animation timers (`CTSAnimation`, also end times in 2.1), the side roll's normalised direction
  (`HandleSlide`), and the 0.1 slow floor in the projectiles' time scale.

## Map entities (issue #100 §3.9, checklist item 10)

`ts21-server`'s `entities` module; decomp `docs/ts21/bots-entities.md` (a) and `rules.md` §9.

* **3.0-only classes don't spawn.** The 33 classes TS 3.0's `mp.dll` exports and 2.1's doesn't
  (`entities::REFUSED_CLASSES`: the twelve new `ts_*` entities, `info_breakable`,
  `info_player_team1..4`, the 16 HLDM weapon and ammo names) fail `DispatchSpawn` and parse no
  keyvalue, as the engine fails a classname 2.1 doesn't export. The reset after a switch spawns

## Protocol (issue #100 §1.2, checklist item 14)

`ts21-server`'s `protocol` module. The wire stays TS 3.0's: the same message table, sizes and
encodings, so both TS 3.0's client and the port's play 2.1 mode.

* **Outgoing messages** (`ServerRules::outgoing_message`, which every message the server sends
  passes): a message written in 2.1's shape leaves in 3.0's. `ScreenFade` (2.1's
  `UTIL_ScreenFade`, FUN_10067180) goes out as `TSFade` with the same 10-byte body; a 13-byte
  `TSFrags` type 0 (2.1's breakable glass) gets 3.0's hit, damage-bits and damage tail (zeros); a
  2-byte `WStatus` gets the count 1 that 2.1's client showed.
* **2.1-only messages** aren't registered, so they can't be sent. `DelObj(idx)` is
  `protocol::del_obj`: `ShowObj(idx, 0)` to everyone. `Flashlight`/`FlashBat` are never sent
  (TS's flashlight is a weapon attachment, `ActItems`); 2.1 registered `GloSlow` and `KAlign`
  but never sent them. `Objective` needs no `ShowObj(idx, 1)` after it: TS 3.0's client makes the
  slot visible itself (0x1004bc50; the decomp's protocol report says otherwise).
* **Player state** keeps 3.0's encodings, which the shared movement reads on both sides:
  `fuser1` 1.0 at normal speed (2.1's 0 would freeze 3.0's movement) and 3.0's `iuser4` stunt
  bits (2.1's glide 0x80000 and super-jump start 0x100000 are 3.0's 0x100000 and 0x200000). Code
  ported from 2.1 converts with `protocol::time_scale` and `protocol::stunt_bits` (and
  `stunt_bits_21` to read).
* `KFuPower` needs nothing (2.1's byte and 3.0's char are the same byte for 0..100), and
  `delta.lst` stays 3.0's.

## Damage (checklist items 4 and 5)

`crates/ts21/server/src/{damage,explode,blades}.rs`, through the damage hooks of
[gameplay-plugins.md](gameplay-plugins.md) §5. Every value was checked in the 2.1 decomp and,
where the decomp hides it (x87 code, call arguments), in the disassembly of `mp.dll`.

**Bullets** (`ShootBulletsPlayer` 0x1003fd40, the bullet manager's update `FUN_1003f910`):

* Each pellet that hits adds `RANDOM_FLOAT(0, 0.05)` to a multiplier that starts at 1.0 once
  per `ShootBulletsPlayer` call, so it **accumulates over the pellets of a shot**: a shotgun's
  `k`-th hitting pellet gets `1 + Σ U(0, 0.05)` over the hits so far. With `damagemult` in force
  (`sv_cheats`) the multiplier restarts from it on every hit. A penetration carries `left × m` on.
  A simulated bullet starts its own multiplier at 1.0 on every update.
* The range-falloff index is truncated (MSVC `__ftol`), for the hit and for the penetration's
  30-unit index; 3.0 rounds.
* Penetration looks `min(left, 48)` past the hit (3.0: `min(2·left, 48)`).
* The traces are the plain `UTIL_TraceLine` (`FUN_10067850`), not 3.0's
  `UTIL_TraceLine_Expanded`: a player's hitboxes outside its box can't be hit.
* `realbullet` does nothing: the weapons read a global nothing writes (`DAT_100aca80`). Only the
  shooter's slow motion fires simulated bullets, stepped every 0.1 s, at the shooter's time scale
  (×0.2 with bullet time; 3.0 has a `1 − s²` curve).
* Bullet damage runs in 2.1's order (`bullet_damage`): `(int)ammo.damage × falloff × mult` for a
  hitscan pellet, `ammo.damage × mult × falloff` for a simulated bullet, from the 2.1 tables'
  `ammo_damage` and `damage_multiplier`; the multiplier is the one the gun used (the silencer's
  `× 0.8` included), recovered from `Shot::damage`.

**The victim** (`TraceAttack` 0x10053310, `TakeDamage` 0x10052cf0, `Killed` 0x10052390):

* Stunting ×0.7 only; no dodge window. A head hit with `DMG_BULLET` doubles, shotgun pellets
  included; thrown blades are never headshots. Legs ×0.5. 2.1 has no `glast_headshot` and no
  headshot kill message, so its hits don't record one.
* Armour covers hitgroups 2..5 against everything but `0x40e0` (so slashing shrapnel is
  covered). A hit no bigger than the armour uses up that much armour and halves; a bigger one
  empties it and deals `dmg − (dmg − armour)`, exactly the armour that was left. That shipped,
  so the plugin does it too. The damage is truncated to an int, as in 3.0.
* Every hit kicks the victim's view up 3° (`punchangle.x -= 3`).
* `Killed` sends no `TSMBlur` (and makes no rolls for it).

**Explosions** (`CM61Grenade::WaitThink` 0x100477e0, `TSExplosion` 0x10047aa0):

* The grenade deals 100, full damage to 128 units, nothing past 1024.
* No dropped gun is pushed.
* Every explosion (grenades and exploding breakables) sprays `RANDOM_LONG(30, 45)` pieces of
  shrapnel from the blast point at 2000 u/s plus the attacker's velocity, each 100 damage
  (`DMG_NEVERGIB | DMG_SLASH`) to the player it touches. The piece is 3.0's `shrapnel` entity
  (`CTSShrapnel`, which 3.0 never creates), made by `entities::ts::shrapnel::create` (a port of
  3.0's dead `CTSShrapnel::Create`); 2.1's `Spawn` leaves it visible (no `EF_NODRAW`) with
  `iuser4 = 1`.
* Then the spectacular slow-motion point is `(0.15, 1.5 s)`.

**Melee** (`crates/ts21/src/shared/melee.rs`, `MeleeRules` on `Ts21`, which both sides run;
`crates/ts21/server/src/melee.rs` for the victim). Entered only on a fresh press, as 2.1's
`PrimaryAttack`/`SecondaryAttack` do. Delays are fixed when set (`× 0.5` with Double Fire Rate
for the blades, `× 6.6666665` with the owner's Slow Pause, else `× T`) and the gun's timers then
count down raw (checklist item 3's timer model).

* **Kung fu** (`FUN_1004de10`): the move table of the decomp's `docs/ts21/weapons.md` §5.4
  (punches 10 ×5 then a heavy `speed/15` in 10..20, kicks, the sweep, the running back kick
  `speed × 0.30303` in 10..90, the flying kick, the airborne cycles), reaches 38/48/56. Damage is
  `base × 0.9 × bar / 100`, so an empty bar deals nothing; the bar loses `base × 0.9` (not The
  One's) and is sent every attack; the Kung Fu power-up doubles the damage. Next attack and idle
  `T × delay`; `BlockPlayer(delay × 0.9)` on the ground. Disarm: an immediate drop when the hit
  deals more than 15, never The One; knockback above 30. No `TSMBlur` roll.
* **Kung-fu block** (`FUN_1004dc70`, the reload key): no bar cost or bar gate, blocks for
  `min(3, 0.3·T)`. The reload key does nothing with a blade.
* **Blocks on the victim** (`FUN_100439e0`): a kung-fu block (or the attacker's own, against a
  victim in a kung-fu attack's delayed window) still lets `(1 − bar/100)` of the hit through to
  the blocker, drains its bar by that, holds it up for its block time left plus `min(3, 0.3·T)`
  and clears its gun's timers. A blade is blocked by the victim's own swing window (knife

* **Katana** (`FUN_1004c090`): `trunc(base × 0.85)`, base 35 above 100 u/s, else 70; backward

* **Knife slash** (`FUN_1004c6c0`): combat 35, seal 15, reach 38, bits `0x1080`, delay

* **Stock hit** (0x1004ab40): only where the 2.1 table has the stock flag (M4A1, Sawed-off), 20
  damage, reach 38, delay 0.725 on all three timers, no stunting change, no disarm or knockback;

* A missed swing's delayed hit opens for `min(3, 0.3·T)`.
* **Jump kick** (`FUN_1005cd00`): the same kick (`speed/15` in 10..20, ×2 with Kung Fu), but no

## Deviations

* **Client prediction uses 2.1 `mp.dll`'s arithmetic, not 2.1 `client.dll`'s.** 2.1's client
  was built without optimisation and rounded more often. The difference is in the last bit only,
  and it made 2.1's prediction disagree slightly with its own server. Following the server keeps
  both sides identical, as the port does for 3.0.

* **Kevlar's loadout bit.** 2.1 marks a bought vest in its own item mask (`+0x690`). The port's
  loadout bit is 3.0's slot-carrying vest, so a 2.1 vest leaves it clear (it weighs nothing).
* **InitHUD's `SrvSett` 0** is Think's `(int)realbullet` copy (3.0's), not `realbullet != 0`;
  the client tests it for non-zero either way.
* **A NULL attacker** in `PlayerKilled` is the world (TS would dereference it).

* A refused classname is matched without case: whether an engine finds a differently cased
  export depends on the engine, and 2.1 has none of these classes in any case.
* `ts_mapglobals`'s weapon mask is applied when the first one spawns, not on the rules' first
  Think. The two differ only if that entity is removed before the first frame.
* A broken breakable or door has no think. 2.1's (FUN_10015e10, the vtable slot 2 default) only
  pushes `nextthink` on by a second, which does nothing.
* `RespawnEntities` runs the plugin API's `BreakableRespawn` hooks (`ham`), as 3.0's does.

* **Floating point.** The crosshair gap and the kung-fu regeneration run on the x87 stack in
  2.1. The port uses f64, which can differ only when a result falls within about 2⁻⁵³ of a
  truncation boundary. The single-precision stores (`NextStunt`, `TSSlowMo / 100`, `now − last`)
  are exact in f32.
* **`default_fov` after a switch** (port addition). After switching away from 2.1, the cvar's
  value is read back from its string, so the 2.1 pin to 80 doesn't carry over into 3.0.

* The client's kick target and a bot's `punchangle` add the kick's yaw as a rounded `float`;
  2.1 adds the unrounded product (at most one ulp apart).
* The server and the client event combine a pellet's direction as TS 3.0's code does (single
  precision); 2.1 sums it on the FPU (at most one ulp apart).
* The client's view-angle kick target uses TS 3.0's smoothing; 2.1's (`FUN_10097de0`) wasn't
  compared.

* **Time scale encoding.** The port keeps 3.0's `fuser1 = 1` for normal time (issue #100 §1.2).
  2.1's `FixedSlowMul` maps its normal 0 to 1; the port's stunt clock maps 1 to 1, and a 0 (which
  2.1 mode never sets) to 10.
* **Bits and animations.** 3.0's `iuser4` layout and animation ids stay (the 3.0 player models).
* **x87 maths in `f64`.** The timer arithmetic (`double` durations, 80-bit products, stored as
  `float`) is done in `f64`; the `float` results can differ in the last bit in rare cases.

* **`PTakeDam`'s amount byte keeps 3.0's encoding** (half the damage, ×8 for shotgun pellets,
  +128 for a kevlar hit), computed from the 2.1 damage. 2.1 sends `min(dmg, 255)`, or 0 for a
  kevlar hit, which a 3.0 client would draw as the wrong blood (issue #100 §1.2: 3.0's wire format
  carrying 2.1 values).
* **Shrapnel without an owner** (an explosion with neither attacker nor inflictor) keeps its
  spawn state; TS would read a null pointer.
* **Melee animations** use the port's (3.0's) animation ids for the matching move: 2.1's table
  numbers the blade swings differently. The kung-fu move ids are the same in both. The `CloseCombat`
  event carries 3.0's view-animation index for the move.
* **The kung-fu block sound** plays when no block is running; 2.1 plays it when the last block
  ended over a second ago, which the port's countdown can't tell.
* **A kung-fu block's damage to the blocker** uses the generic hitgroup and the blocker's origin
  (2.1 passes the attack's trace), and the block's own `PTakeDam` keeps 3.0's encoding. The
  blocker's block animation (0x22) isn't played.

* **Bots' texts are embedded.** 2.1 reads `<gamedir>/bots.txt` and `bot_say.txt`; in 2.1 mode the
  port uses 2.1's shipped files compiled into the plugin (the game directory holds 3.0's), so a
  server can't edit them for 2.1 mode.
* **The observer camera is TS 3.0's** (issue #115): 2.1's `Observer_HandleButtons` cycle has no
  in-eye mode, its `Observer_Idle` copies the target's angles in mode 5, and its `SetMode` holds a
  waiting roaming observer still (maxspeed 1) in the round modes and LMS.
* **Bot guards.** An enemy or listed player whose edict lost its player is skipped (TS keeps a raw
  `CBaseEntity *`). `LookAround` with a `keepGoal` other than 0 or 1 (2.1 would use uninitialised
  angles) leaves the view alone; the port only ever stores 0 or 1. The bots' `fcos`/`fsin` are
  Rust's `cos`/`sin` on `f64`, as for 3.0.
