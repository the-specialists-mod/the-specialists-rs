# The TS 2.1 gameplay plugin

`ts_gameplay 21` makes the server play by TS 2.1's rules, the April 2004 `mp.dll` and
`client.dll`. The decomp's reports are in `docs/ts21/` and posted on issue #100. The plugin is
the crate `crates/ts21` (package `ts21-gameplay`). It plugs into the hooks described in
[gameplay-plugins.md](gameplay-plugins.md), and the 3.0 crates never name it.

## Status

**Skeleton (issue #100 checklist item 1).** The plugin is registered on both sides and
selectable end to end: the cvar, physinfo `gp`, `SrvSett` 4 and the reset on a switch all work.
It overrides no hook yet, so it plays exactly like TS 3.0. Items 2-14 of the issue's checklist
add the 2.1 rules here, each with any hook it needs (added to the 3.0 crates with the 3.0
behaviour as the default).

## Layout

| Package (directory) | Implements | Linked by |
|---|---|---|
| `ts21-gameplay` (`crates/ts21`, `src/shared/`) | `shared::gameplay::PmRules` and `GunRules` on `Ts21`: movement and the gun, which the server and the client's prediction both run (issue §2). The id `"21"` | both libraries |
| `ts21-server` (`crates/ts21/server`) | `ts_server::gameplay::ServerRules` on `Ts21Server` (issue §3), and the server's `PLUGIN` | `server-dll` |
| `ts21-client` (`crates/ts21/client`) | `ts_client::gameplay::ClientRules` on `Ts21Client`: HUD and input (issue §4), and the client's `PLUGIN` | `client-dll` |

The side hooks are packages of their own, not cargo features, so a build of both libraries never
links the server crate into the client library or the other way round
([gameplay-plugins.md](gameplay-plugins.md) §1). `server-dll` registers `ts21_server::PLUGIN`
under the id `"21"` at `GameDLLInit`, and `client-dll` registers `ts21_client::PLUGIN` at
`Initialize`. Both do it behind their default-on `ts21` feature, so `--no-default-features`
builds 3.0 alone.

## Rules

* Match TS 2.1 exactly, including its oddities, as the port matches 3.0 (AGENTS.md). Cite the
  2.1 function and address (`mp.dll`/`client.dll` VAs, `0x1000xxxx`) in doc comments.
* The wire format stays 3.0's (issue #100 §1.2). The plugin carries 2.1 values in 3.0's messages.
* Never copy behaviour that crashes, hangs or stops the engine. Guard it and list it below.

## Client: HUD and input (checklist item 13)

`ts21-client` overrides these `ClientRules` hooks ([gameplay-plugins.md](gameplay-plugins.md)
§5). The HUD picks them from `SrvSett` 4. Addresses are 2.1 `client.dll` VAs, checked in the
disassembly.

| Area | TS 2.1 | Evidence |
|---|---|---|
| Crosshair | One gate for the whole draw: nothing at all (no crosshair, laser number or divesteps) for weapons 0/24/25/34/35, or for the Barrett (18) unless `m_iFOV < 40`. That FOV test runs before third person clears the scoped flag. Otherwise the crosshair is drawn first and the divesteps on top. | `0x1008b960` |
| Crosshair gap | `ftol(base + ((float)(acc + spread) − acc) / 0.1f × 16)`, with `acc` the weapon's table accuracy. The float store and the `/ 0.1f × 16` can land a pixel short of 3.0's `base + spread × 160`. | `0x1008bb67` |
| Divesteps | Top dive blocked at `used > 21`, or with kevlar when `m_Teamplay > 1`. Centre blocked at `> 41`, bottom at `> 71` (signed compares). | `0x1008c0f0`/`c160`/`c190` |
| Stunt cooldown colour | `NextStunt` stores `m_flTime + (float)n / 10`. The divesteps are red until that time has passed. This runs on real time, so slow motion doesn't stretch it. | `0x1008d6a0`, `0x1008c1cf` |

**Corrections to issue #100 §4 and the decomp's `client-protocol.md`, from the disassembly:**

* The report says `SetFOV` is applied instantly in 2.1. It isn't: 2.1 eases the FOV with the same
  step as 3.0. The differences are the pinned `default_fov` and the wider snap range above.
* The divesteps also differ in the cooldown clock and in draw order.
* The 2.1 client has a kung-fu regeneration of its own, and its `Reset` refills the bar.

**Integration points with the other items:**

* **Weapon and ammo tables (item 3).** The 2.1 client hard-codes its weapon and ammo tables
  (`0x1001e270`, `0x10299308`). They hold the same buy data as the 2.1 server table (prices,
  slots, attachment masks, ids 8 and 17, no 2/29/36/37). The buy menu, the crosshair's `accuracy`
  and the weapon panel still read `shared::weapons::tables()`, which is 3.0's. Once the 2.1 table
  set exists, they should read the active ruleset's tables, and then no separate client list is
  needed. Until then, the 2.1 buy menu shows 3.0 prices and slots.
* **The crosshair's spread (item 3).** In 2.1 the crosshair's copy of the spread penalty
  (`0x1031bf04`) changes only in the prediction's decay branch, and weapon deploy (`0x10026210`)
  zeroes it. That copy is `state.spread`, which client prediction sets.
* **Protocol (item 14).** The 2.1 client sets the kung-fu bar from `WeaponInfo`'s clip when the id
  is 0. A 2.1-mode server that sends `KFuPower` on every change makes that unnecessary.

**Not done:**

* The buy menu's display. This covers the hard-coded English strings, the item rows' colours, the
  category page's mouse rows (in mode 1, 2.1's drawn "Go Back" row sends key 6), and the
  cash-based summary header. The header is 3.0 code that is dead while `CashBased()` is off; the
  port also gets its ammo total wrong, see the issue filed for it.
* 2.1's other HUD looks (kung-fu bar alphas, status panel layout and labels). The port keeps 3.0's
  HUD look.
* 2.1's extra commands `+strafe`, `+mlook` and the empty `buyitem`/`buylast`. Client commands are
  registered once at `Initialize`, and registering them would change 3.0 mode.
* The HLTV spectator's key handling.

## Deviations

* **Floating point.** The crosshair gap and the kung-fu regeneration run on the x87 stack in
  2.1. The port uses f64, which can differ only when a result falls within about 2⁻⁵³ of a
  truncation boundary. The single-precision stores (`NextStunt`, `TSSlowMo / 100`, `now − last`)
  are exact in f32.
* **`default_fov` after a switch** (port addition). After switching away from 2.1, the cvar's
  value is read back from its string, so the 2.1 pin to 80 doesn't carry over into 3.0.
