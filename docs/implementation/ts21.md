# The TS 2.1 gameplay plugin

`ts_gameplay 21` makes the server play by TS 2.1's rules, the April 2004 `mp.dll` and
`client.dll`. The decomp's reports are in `docs/ts21/` and posted on issue #100. The plugin is
the crate `crates/ts21` (package `ts21-gameplay`). It plugs into the hooks described in
[gameplay-plugins.md](gameplay-plugins.md), and the 3.0 crates never name it.

## Status

The plugin is registered on both sides and selectable end to end: the cvar, physinfo `gp`,
`SrvSett` 4 and the reset on a switch all work (issue #100 checklist item 1).

Done:

* **Item 2, shared movement:** every row of issue §2.1, speed by free slots (§2.2) and the 310
  cap ([Movement](#movement)).
* **Items 10, 14:** the map entities and the protocol translation
  ([Map entities](#map-entities-issue-100-39-checklist-item-10), [Protocol](#protocol-issue-100-12-checklist-item-14)).
* **Items 6, 7, 11:** the server rules, scoring, cash, cvars and commands
  ([Rules, scoring, cash, cvars and commands](#rules-scoring-cash-cvars-and-commands-issue-100-items-6-7-11)).

Every other hook keeps TS 3.0's body. The remaining items of the issue's checklist add the 2.1
rules here, each with any hook it needs (added to the 3.0 crates with the 3.0 behaviour as the
default).

## Layout

| Package (directory) | Implements | Linked by |
|---|---|---|
| `ts21-gameplay` (`crates/ts21`, `src/shared/`) | `shared::gameplay::PmRules` and `GunRules` on `Ts21`: movement and the gun, which the server and the client's prediction both run (issue §2). The id `"21"` | both libraries |
| `ts21-server` (`crates/ts21/server`) | `ts_server::gameplay::ServerRules` on `Ts21Server` (issue §3), and the server's `PLUGIN` | `server-dll` |
| `ts21-client` (`crates/ts21/client`) | `ts_client::gameplay::ClientRules` on `Ts21Client`: HUD and input (issue §4), and the client's `PLUGIN` | `client-dll` |

The side hooks are packages of their own, not cargo features, so a build of both libraries never
links the server crate into the client library or the other way round
([gameplay-plugins.md](gameplay-plugins.md) §1). `server-dll` registers `ts21_server::PLUGIN`
under the id `"21"` at `GameDLLInit`, and `client-dll` registers `ts21_client::PLUGIN` at
`Initialize`. Both do it behind their default-on `ts21` feature, so `--no-default-features`
builds 3.0 alone.

## Rules

* Match TS 2.1 exactly, including its oddities, as the port matches 3.0 (AGENTS.md). Cite the
  2.1 function and address (`mp.dll`/`client.dll` VAs, `0x1000xxxx`) in doc comments.
* The wire format stays 3.0's (issue #100 §1.2). The plugin carries 2.1 values in 3.0's messages.
* Never copy behaviour that crashes, hangs or stops the engine. Guard it and list it below.

## Movement

`crates/ts21/src/shared/pm.rs` (`PmRules` on `Ts21`). The server and the client's prediction
both run it, chosen per command by physinfo `gp`, so they agree. Addresses are 2.1 `mp.dll`'s
(decomp `ts21/server-win`, report `docs/ts21/movement.md` §2). Each value was checked against the
disassembly and the constants in `.rdata`.

| What | TS 2.1 | Hook | 2.1 address |
|---|---|---|---|
| Ground acceleration while not prone or ducked | the `double` 0.7, multiplying the unrounded product (3.0: `PM_GetAccelBySpeed`, 0.6..1.1) | `ground_accel` = `Constant(0.7)` | `PM_Accelerate` 0x100315f0, 0.7 at 0x10082938 |
| Input while `RECOVER` | moves × the `double` 0.1 (3.0: 0.5) | `recover_input_scale` | `TSHandle` 0x10058400, 0x10080200 |
| Forward input while `PRONE` | × the `double` 0.0 (keeps a -0 or a NaN; 3.0 stores 0) | `prone_forward_scale` | 0x10058478 |
| Wall jump | `v.xy = -170·forward.xy`, `v.z = sqrt(80000)` = 282.84271 (3.0: 210, 236.64319) | `wall_jump_speed`, `wall_jump_up_velocity` | `TSWallJump` 0x100581d0 |
| Wall climb | `v.z = sqrt(96000)` = 309.83865 (3.0: 334.664) | `wall_climb_velocity` | `TSWallJumpClimb` 0x10058270 |
| Wall dive | none: the dive always follows the velocity, `WALLDIVE` is never read or cleared | `wall_dive` = false | `TSDive` 0x100582d0 |
| `FixVelocity(v, lim)` | if the 3D speed `L` (stored to a `float`) is above `lim`: `v.x *= lim/L` (the unrounded ratio), `v.y *=` the stored ratio; z untouched. After the dive, wall jump and wall climb with `2·maxspeed` (3.0's is empty) | `fix_velocity` | 0x10057d10 |
| Strafe jump | with `IN_MOVELEFT`/`IN_MOVERIGHT` held: `v.xy += 100·normalize(v).xy`, then `FixVelocity(v, maxspeed)`, then the normal 236.64319 up (3.0: nothing) | `jump_push(Normal)` | `PM_Jump` 0x10058680 (0x100589a5) |
| Super jump | `v.xy += 100·normalize(v).xy`, unclamped, then 400 up | `jump_push(High)` | 0x10058911 |
| Frame time scale | a time scale (`fuser1`) of 0 is normal speed; otherwise frozen below 0.1 | `scaled_frametime` | `PM_PlayerMove` 0x10033cd5 |
| Punch decay | not zeroed while dead; the length is stored to a `float`, then `len - (0.5·len + 10)·frametime·(fuser1 ? fuser1 : 1)`, clamped at 0 | `drop_punch_angle` | `PM_DropPunchAngle` 0x10033b10 |
| Footstep interval in slow motion | `(int)(interval / fuser1)` when `fuser1 != 0`, no 0.1 floor (3.0: `interval / max(fuser1, 0.1)`) | `step_interval` | `PM_UpdateStepSound` 0x10030dad |
| Speed by free slots | `free >= 70 ? 310 : (int)(free·(1/70.f)·140 + 170)`, 170..310; no The One speed (3.0: 210..330, The One 330) | `speed_by_slots` | `GetSpeedBySlots` 0x100436e0 |
| Speed cap and spawn speed | `SetPlayerSpeed` clamps to 0..310; `TSInit` calls `SetPlayerSpeed(310)` (3.0: 330) | `max_player_speed` | 0x100557b0, `TSInit` 0x100552f0 |

The rest of the movement is the same in both builds and isn't overridden. That includes the
super-jump glide: 2.1 reads it from `iuser4` bit 0x80000 (3.0: 0x100000), and its super jump
sets 0x100000 (3.0: 0x200000). The shared movement keeps 3.0's bit layout, as the wire does
(issue #100 §1.2), and the server's stunt code converts. The time scale also keeps the port's
encoding, where 1.0 is normal (2.1 uses 0), so the 2.1 guards for 0 only matter before a
player's first spawn.

### Arithmetic

* 2.1 `mp.dll` runs the x87 at 53 bits, as 3.0's does (its CRT sets `_PC_53` at 0x1006fa8b), so
  `Arith::Msvc` reproduces its finite arithmetic. The overrides reproduce its stores and
  operation order, written generically over `shared::pm::Fpu`.
* 2.1's compiler tests `fcom` through the parity flag, so its comparisons follow IEEE for a NaN
  (Rust's operators). The overrides use IEEE compares. The SDK movement code both rulesets
  share still sends a NaN 3.0's way: issue #105.
* 2.1's `client.dll` is an unoptimised build that stores every intermediate to a `float`
  (`PM_Accelerate` cl21 0x1005aef0, `FixVelocity` cl21 0x100919b0), so 2.1's own prediction
  could differ from its server in the last bit. The port predicts with the server's arithmetic
  instead, so client and server agree exactly (see Deviations).
* TS 2.1 shipped no Linux server. With the server's `ts_pm_arith gcc`, the overrides run 2.1's
  formulas with `ts_i386.so`'s rounding (every value the C stores rounded to a `float`). There is
  no 2.1 GCC build to compare against.

## Rules, scoring, cash, cvars and commands (issue #100 items 6, 7, 11)

`ts21-server` (`crates/ts21/server/src/`): `rules.rs`, `scoring.rs`, `cash.rs`, `players.rs`,
`cvars.rs`, `commands.rs`. Addresses are 2.1 `mp.dll` VAs; decomp `docs/ts21/rules.md`.

### Game modes and teams (`rules.rs`)

* **The mode comes from the map name** (`DecideGamePlay` 0x100433b0, case-sensitive prefix):
  `tm_` objective rounds (3), `tr_`/`cs_`/`de_` round team deathmatch (2), `ts_` teamplay in The
  One mode, else `mp_teamplay`. There is no worldspawn `gamemode` key. `mp_theonemode` is read at
  map load; on a map that isn't `ts_` The One still runs, on DM rules.
* **LMS is the live `lastmanstanding` cvar** in DM (Think reads it every frame), not a mode.
* **Round modes 2/3** (`InstallGameRules`, `CTSGameRules::Init` 0x10044810): teams "Specialists"
  (model `seal`) and "Mercenary" (`merc`), each with team cash `(int)initial_cash`; the first
  round starts 5 s in. `InitObjectives` makes it mode 3 when the map has a
  `ts_objective_manager` (at every round restart; at install no entity exists yet, so the first
  5 s are mode 2, as in 2.1). Specialists spawn at `info_player_start`, Mercenaries at
  `info_player_deathmatch`, and in mode 2 the sides swap every third round.
* **Rounds:** Think's round branch, `TeamWin(team, win, lose)` (0x10044d00: team cash
  `min(max(c + win, initial), 30000)` for the winner, `max(c + lose, initial)` otherwise; with
  under two players the team cash and scores start again and "Waiting other players."),
  `RestartRound` (0x100445d0: no refund, players pick up their team cash, join deadline 25 s,
  respawn in 3 s), `ResetRestartRound` (0x10044ba0, restart in 3 s; `n >= 2` also clears the team
  cash and scores), `CheckDeads` (0x10045940: LMS counts a pending respawn as standing; mode 2
  team wins and draws). `TSHVoice` and the "Specialists"/"Mercenary" `TeamScore`s.
* **Teamplay on DM maps** is the SDK's model teams: the team list is `mp_teamlist` (no 4-team
  table, no `mapteams`/`teammodels`/`mp_teammodels`), `SetDefaultPlayerTeam` reads the `model`
  key, and each team's model is its name. In The One mode the players' models and teams are
  `mp_theone` and `mp_theothers`.
* **The One:** `SetPlayerTheOne` (0x100467c0) without the speed change or log line;
  `SelectRandomTheOne` (0x100466e0) doesn't look for a One first, and Think calls it every frame
  while there is none, plus the 10 s check; after a kill The One gains 10 health per player up to
  200 (teamplay `PlayerKilled` 0x100392e0, counting slots 0..maxClients-1 as compiled); overheal
  decays to 100 for everyone, The One included, and nothing regenerates.

### Scoring (`scoring.rs`)

`TSGetPointsForFrag` (0x1004f3c0) and `PlayerKilled` (0x1004f7e0): a stunt kill +2 with no speed
test, a slide +1, both stacking on close combat (kung fu + stunt = 4); round modes score plain
points; English frag messages (`"%i frags for %s, %s"`, " style!", "Kung-Fu"); double kill
within 1 s, the last-kill time always updated; sprees +30 / +50 / health set to 150 with kung fu,
super jump and a 3 s slow pause; killing The Specialist +5 and a 3 s slow pause; no specialist
suicide penalty; no headshot/knife/katana/coldcock lines; death-cam slow point 0.15 for 1.5 s;
`slowmatch` caps the held slow motion at 5 s. A suicide or a death by a non-player takes the frag
from the **attacker's** pev (0x1004f87f): a world kill costs the world a frag and the victim
keeps its frags. Kill logs carry no 3.0 tags.

### Cash and buying (`cash.rs`, `players.rs`)

* `CashBased()` (0x100435f0): the round modes, or Think's `(int)usecash` copy non-zero.
* Join: `InitHUD` sets the cash to `(int)initial_cash` (no `ClientPutInServer` cash). The floor
  `FUN_10042c90` (team cash in the round modes, then `initial_cash`) runs at `StartObserver`,
  `Killed` and `TSInit`.
* Kill cash: points × 900, only in DM/TDM while cash-based.
* `BuyArmament`, `BuyWeapon`, `AddItem`, `BuyAmmo` (0x100559d0, 0x10055e00, 0x10055c30,
  0x10055a40): the weapon's cost and the attachments (silencer 900, laser 800, flashlight 500,
  scope 1800) are charged when cash-based and refused below 0; M61s only in the round modes, two a
  life; kevlar (1900) and stealth shoes (700) only in the round modes; kevlar sets the armour to
  100 and weighs nothing.
* `Killed` in DM/TDM drops an armour power-up holding the remaining armour.
* Respawns (`SetPlayerRespawnTime` 0x10042d50): mode 3 by `ts_mapglobals` `playerrespawn`, mode 2
  and LMS by `respawnnumber`, join deadline 25 s.

### Cvars and commands (`cvars.rs`, `commands.rs`)

* Registered besides 3.0's: `mp_flashlight` "0", `initial_cash` "3000", `cashforwin` "1500",
  `cashforlose` "-1000", `respawnnumber` "1" (`ServerRules::cvars`; the server has the union).
  `respawntime` keeps 3.0's default "3": both clamp it to 5..30, so it plays as 2.1's "5".
* `globalslow`, `weaponrestriction` and `restartround` are cvars 2.1 polls in Think. The engine
  can't register a cvar named like a command, so 3.0's commands stay and, in 2.1 mode, act as the
  cvar: no argument prints `"name" is "value"`, an argument sets it. `globalslow` is a fraction
  clamped to 0..1 (0..2 with cheats), 1 meaning off; `weaponrestriction` 1..5 map to masks
  0, 0x01, 0x03, 0x13 and 0x1f (5 ignoring the map), sent as `SrvSett` 3 on change;
  `restartround n` restarts and goes back to 0.
* `SrvSett` 0 carries `realbullet != 0`.
* Client commands: `give <class>` (cheats), `powerup 4` stores a timed infinite clip (type 2),
  `cashala` +10000; `respawn`, `motd`, `fullupdate` and `lasclr_*` are unknown commands.

## Map entities (issue #100 §3.9, checklist item 10)

`ts21-server`'s `entities` module; decomp `docs/ts21/bots-entities.md` (a) and `rules.md` §9.

* **3.0-only classes don't spawn.** The 33 classes TS 3.0's `mp.dll` exports and 2.1's doesn't
  (`entities::REFUSED_CLASSES`: the twelve new `ts_*` entities, `info_breakable`,
  `info_player_team1..4`, the 16 HLDM weapon and ammo names) fail `DispatchSpawn` and parse no
  keyvalue, as the engine fails a classname 2.1 doesn't export. The reset after a switch spawns
  the map through the same `dispatch_spawn`, so a switch to 2.1 drops them and a switch back
  brings them back. The client doesn't run the map's own effects in 2.1 (`ClientRules::map_effects`):
  no `ts_emitter`/`ts_particle` emitters and no `ts_fog` fog, which the 3.0 client reads from the
  BSP itself (2.1's `client.dll` has neither).
* **Keyvalues.** Keys 2.1's classes don't have are refused (`fHandled` 0): `respawntime`,
  `respawntarget` (breakables, pushables, doors), `buyable`, `attackerteam` (`ts_groundweapon`),
  `attackerteam` (`ts_trigger`), `pwupmult` (`ts_powerup`), and every `ts_objective_ptr` key but
  `objmsgspec`/`objmsgmerc`. `ts_trigger`'s `allowedteam` is stored as is (3.0 turns 2 into
  "anyone"). `ts_mapglobals` reads `playerrespawn` and `playeratatime` (KeyValue 0x10042090),
  which 3.0 ignores, into `MapGlobals`.
* **`ts_trigger`** (`WaitTouch` 0x10040c00): `allowedteam` 0 fires only for a player whose
  `TeamID()` is "Specialists", 1 only for "Mercenary" (`stricmp`), 2 or more for anyone, a
  negative value for no one; a trigger without the key is 0. No `message`, no case-carrier
  spawnflag 8.
* **`ts_groundweapon`.** Picked up by touching it while holding +use (`WaitTouch` 0x10066440),
  as well as by `Use`. `GetWeapon` (FUN_10066250) has no price or team check, shows `message` at
  the top (`TSHudMessageOne` effect 1, 3.0's is 8) and plays the extra clip's sound at normal
  pitch. Landing (`OnGround` 0x10066190) makes it `MOVETYPE_FLY` with `effects |= 2`.
* **`ts_mapglobals`.** Only the first one counts (2.1's rules read it once, on their first Think),
  and only for the weapon mask (`spawnflags ^ 0x1f`): flags 32 (no round timer) and 64 (super
  jump for all) do nothing. `entities::map_globals_keys()` gives `(playerrespawn, playeratatime)`
  as the bytes 2.1's rules keep (`CTSGameRules+0x54cc`/`+0x54cd`), for the objective mode's
  `SetPlayerRespawnTime` (FUN_10042d50).
* **Breakables and doors.** A broken `func_breakable` or door stays broken (`Die` 0x10042540,
  `CBaseDoor::TraceAttack` 0x10013c50 schedule nothing). `entities::respawn_entities(force)` is
  2.1's `RespawnEntities` (0x10044400): `BreakableRespawn(force)` on every `func_breakable`,
  `func_door` and `func_door_rotating` by classname (not `func_pushable` or `func_water`),
  restoring at once with no wait for players in the way and no target; then `Fall` on the ground
  weapons (round modes 2/3 or `lastmanstanding`) and the power-ups (`lastmanstanding`). It runs
  every 60 s from the deathmatch/teamplay Think unless `lastmanstanding` is on in deathmatch
  (the 2.1 Think, `rules::think`, with the timer at `CTSGameRules+0x1b8` that `Init` starts at
  now + 60), and forced from `RestartRound` (`rules::restart_round`).

Still to connect: the objective mode's respawn limit should read `entities::map_globals_keys()`
(the rules read `ts_mapglobals` themselves for now).

## Protocol (issue #100 §1.2, checklist item 14)

`ts21-server`'s `protocol` module. The wire stays TS 3.0's: the same message table, sizes and
encodings, so both TS 3.0's client and the port's play 2.1 mode.

* **Outgoing messages** (`ServerRules::outgoing_message`, which every message the server sends
  passes): a message written in 2.1's shape leaves in 3.0's. `ScreenFade` (2.1's
  `UTIL_ScreenFade`, FUN_10067180) goes out as `TSFade` with the same 10-byte body; a 13-byte
  `TSFrags` type 0 (2.1's breakable glass) gets 3.0's hit, damage-bits and damage tail (zeros); a
  2-byte `WStatus` gets the count 1 that 2.1's client showed.
* **2.1-only messages** aren't registered, so they can't be sent. `DelObj(idx)` is
  `protocol::del_obj`: `ShowObj(idx, 0)` to everyone. `Flashlight`/`FlashBat` are never sent
  (TS's flashlight is a weapon attachment, `ActItems`); 2.1 registered `GloSlow` and `KAlign`
  but never sent them. `Objective` needs no `ShowObj(idx, 1)` after it: TS 3.0's client makes the
  slot visible itself (0x1004bc50; the decomp's protocol report says otherwise).
* **Player state** keeps 3.0's encodings, which the shared movement reads on both sides:
  `fuser1` 1.0 at normal speed (2.1's 0 would freeze 3.0's movement) and 3.0's `iuser4` stunt
  bits (2.1's glide 0x80000 and super-jump start 0x100000 are 3.0's 0x100000 and 0x200000). Code
  ported from 2.1 converts with `protocol::time_scale` and `protocol::stunt_bits` (and
  `stunt_bits_21` to read).
* `KFuPower` needs nothing (2.1's byte and 3.0's char are the same byte for 0..100), and
  `delta.lst` stays 3.0's.

## Deviations

* **Client prediction uses 2.1 `mp.dll`'s arithmetic, not 2.1 `client.dll`'s.** 2.1's client
  was built without optimisation and rounded more often. The difference is in the last bit only,
  and it made 2.1's prediction disagree slightly with its own server. Following the server keeps
  both sides identical, as the port does for 3.0.

* **Kevlar's loadout bit.** 2.1 marks a bought vest in its own item mask (`+0x690`). The port's
  loadout bit is 3.0's slot-carrying vest, so a 2.1 vest leaves it clear (it weighs nothing).
* **InitHUD's `SrvSett` 0** is Think's `(int)realbullet` copy (3.0's), not `realbullet != 0`;
  the client tests it for non-zero either way.
* **A NULL attacker** in `PlayerKilled` is the world (TS would dereference it).

* A refused classname is matched without case: whether an engine finds a differently cased
  export depends on the engine, and 2.1 has none of these classes in any case.
* `ts_mapglobals`'s weapon mask is applied when the first one spawns, not on the rules' first
  Think. The two differ only if that entity is removed before the first frame.
* A broken breakable or door has no think. 2.1's (FUN_10015e10, the vtable slot 2 default) only
  pushes `nextthink` on by a second, which does nothing.
* `RespawnEntities` runs the plugin API's `BreakableRespawn` hooks (`ham`), as 3.0's does.
