# Client display audit, round 3 (3.0 + 2.1)

Round 3 audits the client's graphical display and GUI (model rendering, HUD and effects, VGUI menus) against 3.0's and 2.1's `client.dll`, function by function: draw order, positions, sizes, fonts, colours, alpha, sprites and models, timers and fades, cvars, rounding, gating, and the messages handled. The table format is [client.md](client.md)'s (port function | 3.0 original | 2.1 original | status). This round each group also fixed what it found, so the issues below are closed by commits on the group's branch. Decomp helpers: `scripts/round2/fn.sh client|ts21/client <addr>`, `dis.sh cl|cl21`, `rd21.py`.

### Not verified
- ~~The 3.0 renderer's sub-ulp float forms aren't replicated.~~ Round 4: **MISMATCH #276 (both), fixed** (`ClientRules::float_form`). The port's f32 arithmetic matched neither build, and not only in the last bit: the player blend truncated a rounded `pitch × 3` (pitch `0xc1e2aaaa`: byte 7, TS 8) and computed `255·(b − s)/(e − s)` in f32 (190 vs TS 191 for one range), and the 0.01 interpolation test and the 0.2 previous-sequence test added in f32. 3.0 (`FloatForm::Optimised`): `×10` (`0x10030c76`), `×5` (`0x10031476`), `× 1/255` (the double `0x10079e68`, not a float), `× ⅓` (`0x1007d670`), values on the x87 until the float argument; the controllers keep the value through the clamp, lerp and `× π/180` (double `0x1007d518`). 2.1 (`Unoptimised`): `/0.1` (`0x10064575`), `/0.2` (`0x1006527b`), `/255.0` (`0x10064e46`, `0x10063008`), `/64.0`, `/3.0` (`0x10063d3f`), each statement stored to its float. NaN tests per build (3.0 `test ah,1`/`0x41; je`, 2.1 `jp`).
- ~~2.1 `StudioEstimateFrame` (0x10064b00): the decompile is empty.~~ Round 4: traced in the asm (0x10064b00..0x10064c78). It is the SDK's, in doubles, and matches the port: `dfdt = (time − animtime)·framerate·fps` when interpolating and `animtime ≤ time` (else 0), `f = frame·(n − 1) / 256.0` for `n > 1`, `+ dfdt`; looping `f −= ftol(f/(n − 1))·(n − 1)` and `+ (n − 1)` below 0; else `n − 1.001` when `f ≥` it, and 0 below 0; returned as a double (`fst` leaves it on the stack). The only difference from 3.0 is NaN handling in the `< 0` tests, now per `float_form` (#276). The `fcomp prevframe` at 0x10064d60 in `StudioSetupBones` is a dead compare (no branch reads it).
- ~~2.1's `ev_punchangle` (0x10320fd0) is non-zero there.~~ Round 4: it isn't. `V_CalcGunAngle` (0x100b6610) does add `∓1.25 × ev_punchangle`, but its writers that look like a kick, 0x10096310 (a rapid-fire pitch punch) and 0x100964a0 (a sided kick through 0x1031b7f4), are dead: their thunks 0x10003e40 / 0x10002239 are never called, and no relocated pointer names them. 0x1008b960 is the crosshair draw, not a writer. The only live writer is the `KAlign` handler 0x10088480, and 2.1's mp.dll registers `KAlign` (0x1002a86e) without ever sending it; the rest are the reset 0x10026210 and `V_DropPunchAngle`. So the gun's punch terms are 0 in 2.1 as in the port: no change. Round 3's "`apply_kick` vs 0x10097de0: match" was the algorithm; the documented ts21.md deviations were its float forms: **MISMATCH #278, fixed** (2.1 stores `target − cur`, `|d|²` and both steps to floats, a NaN length keeps easing; and the kick target adds 2.1's unrounded yaw product, client 0x1001ea26 / bots' `punchangle` server 0x10049c7c).
