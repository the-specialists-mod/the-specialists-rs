## Description

Client differences from TS's \`client.dll\`, found while working on #72:

1. **\`CHud::VidInit\` resets only the current time scale.** At 0x100208a9 TS writes 1.0 to \`g_flTimescale\` (0x100963e8) only. The target (0x1009ff04) is written only by the \`TSSlowMo\` handler (0x1004bf10 / 0x1004bf23). The port's \`hud::vid_init\` (\`crates/client/src/hud/mod.rs:439-440\`) resets both, so slow motion that's still active isn't eased back in after a level change the way TS does it.
2. **The \`Spectator\` handler resets the local prediction object.** For the local player TS calls \`FUN_10004600\` (0x100652fd), which runs \`FUN_1000b9d0\` (\`unnamed_1000b9b0.c:20\`). That zeroes \`+0x764..+0x770\` on the local-player prediction object, plus the globals 0x10191480/84/88 and 0x1018d188. Work out what these are and port the reset.
3. **The per-player observer flag.** TS stores the raw byte (\`0x101900ec[i]\`, written at 0x101901f5). The port stores \`observer != 0\` (\`hud/state.rs\`, \`players[cl].observer\`). Check whether any reader tells the values apart.
4. **The emitter frame time is clamped.** \`view::frame\` clamps the frame time to 0–0.25 (\`crates/client/src/view.rs:514\`) before \`effects::frame\`. TS's emitter frame (0x1003ab40) gets the raw \`HUD_Frame\` time. Verify, then match TS.
5. **\`WeaponInfo\` id 0xff.** TS keeps the old id only when the read runs off the end of the message. \`READ_BYTE\` (0x10029a10) zero-extends, so 0xff becomes weapon 255. The port treats 0xff as "keep" (\`shared/src/protocol/hud.rs:266\` and the WeaponInfo branch in \`hud/state.rs\`). The port's server never sends 0xff, so this is low priority.
