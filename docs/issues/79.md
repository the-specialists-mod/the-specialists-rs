## Description

Client differences from TS's \`client.dll\`, found while working on #77 and #78. Each was checked in both the binary and the port.

1. **View-anim body.** TS's client \`SendWeaponAnim\` (0x10003680) ignores its body argument and uses the gun's \`pev->body\` (\`mov 0x114(%ecx)\` at 0x10003695). The port passes the shared code's body, which is 0 at e.g. \`crates/shared/src/weapons/gun.rs:980\` and \`:1044\`, through \`ClientHost::weapon_anim\` (\`crates/client/src/prediction/gun.rs\`).
2. **Akimbo right clip.** TS computes \`right = clip - left\` and sets it to 0 when it's below 1 (\`setle/dec/and\` at 0x10003ae1–0x10003aed). \`crates/shared/src/protocol/weapons.rs\` (\`s.right = s.clip - s.left\`) doesn't clamp, so it can go negative.
3. **\`ItemPostFrame\` gate.** TS runs \`ItemPostFrame\` when \`pev->deadflag != 5\`, \`FUN_10026860()\` is false and \`m_flNextAttack <= 0\` (0x10003d4b–0x10003d76). The port uses \`!dead\` (\`deadflag != 0 || health <= 0\`) plus \`Gun::post_frame_ready\` (\`prediction/gun.rs\`), which also passes for kung fu and for +cancel during a reload.
4. **Rain doesn't lead the player.** For camera-centred spawning (cameradensity and cameraradius > 0.01, camera inside the box), TS adds 1.5 × the local player's velocity to x/y (0x1003b0a0–0x1003b0cb: \`GetLocalPlayer\`, \`curstate.velocity\` at +0x320/+0x324, the 1.5 at 0x1007a860). The port's emitter (\`crates/client/src/effects/emitters.rs\`) doesn't, so rain spawns around the camera without moving ahead of a running player.
